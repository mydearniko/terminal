# Findings & Decisions: Terminal query reply leakage

## Requirements
- Stop terminal query replies from appearing as typed input in tmux, Codex, and other TUIs.
- Cover the observed `11;rgb:1e1e/1e1e/1e1e` and `52c` fragments plus OpenAI Codex issue #31420.
- Preserve terminal functionality; do not solve this by globally disabling color/device/status queries.
- Reassess the previously delivered BEL-only OSC workaround because it did not solve the full problem.
- Provide rigorous regression evidence and, if delivery remains in scope, a fully verified replacement installer.

## Known Starting Evidence
- The previous source change altered `_ReturnOscResponse()` so 7-bit OSC color replies end in BEL while S8C1T retains C1 ST.
- The prior Windows build compiled and passed 407 adapter tests, but those tests asserted generated bytes and did not reproduce the user's installed end-to-end environment.
- User reports the installed version still leaks `11;rgb:1e1e/1e1e/1e1e` when opening tmux.
- User reports Codex can receive/type `52c` and points to https://github.com/openai/codex/issues/31420.
- These symptoms span at least OSC color and another likely CSI/device-report family, indicating the shared reply/input path is more relevant than one terminator.

## Research Findings
- Codex issue #31420 identifies `52c` as the end of Windows Terminal's full primary Device Attributes reply: `ESC [ ? 61;4;6;7;14;21;22;23;24;28;32;42;52 c`. In the captured failure the prefix through the first digit of parameter 22 arrived before Codex's 100 ms probe deadline, while the 20-byte tail `2;23;24;28;32;42;52c` arrived afterward.
- The repository produces that exact PDA payload in `AdaptDispatch::PrimaryDeviceAttributes()` (`adaptDispatch.cpp` around line 1456), confirming the mapping is not speculative.
- Issue #31420's primary demonstrated failure is an application ownership/timeout race: Codex stops its startup-probe reader at a fixed deadline and hands stdin to normal event processing while a solicited reply is incomplete. The delayed tail is therefore interpreted as keys; leading ASCII `2` selects “No, quit.”
- The deterministic issue reproducer is terminal-independent: a Python PTY harness deliberately splits a standards-compliant PDA response by 350 ms. A Codex-side bounded drain of the incomplete response fixes that scenario without disabling keyboard probing.
- A later issue comment reports a broader Codex manifestation containing complete CPR, OSC 10/11, kitty keyboard flags, PDA, focus events, and real keystrokes. The commenter independently verified the terminal/multiplexer forwarded bytes completely and in order, placing that particular leak at Codex's startup-reader/EventStream handoff.
- The later comment correctly notes that a PDA-only Codex drain is insufficient for arbitrary delayed batches; robust application-side handling needs one incremental stdin demultiplexer or bounded outstanding-response state spanning all sent probes.
- Windows Terminal has many response producers across CSI, DCS, OSC, and a direct VT52 response. `_ReturnOscResponse()` is only one of them; the prior BEL change cannot affect PDA/`52c`, CPR, keyboard flags, mode reports, or DCS responses.
- Standards-compliant terminal replies are delivered through the same input byte stream as keyboard/focus events. A terminal cannot generally distinguish “the application is no longer waiting” from “the application is still parsing,” so terminal-side suppression after an arbitrary deadline would necessarily remove functionality.
- tmux 3.5a actively sends `OSC 10;? ST` and `OSC 11;? ST` during terminal capability/default-color discovery (`tty.c`). Thus the user's tmux startup text is a solicited terminal reply, not an unsolicited Windows Terminal emission.
- tmux 3.5a has dedicated parsers for primary/secondary/extended Device Attributes and treats partial prefixes specially; its pane-output OSC parser also recognizes both BEL and ST terminators. The separate client-terminal color-reply parser still needs targeted comparison against 3.6b.
- The local environment is currently tmux 3.6b; the earlier validation's upgrade away from 3.5a is now treated as a possible coverage gap rather than evidence that all deployed tmux versions are safe.
- tmux 3.5a's client-terminal parser calls `tty_keys_colours()` before treating bytes as keys. It recognizes an OSC 10/11 prefix, returns “partial” until a terminator arrives, and accepts both BEL and `ESC \\`; the 3.6b diff does not introduce BEL support. Therefore the BEL change is not, by itself, incompatible with tmux 3.5a.
- tmux consumes recognized terminal replies as `KEYC_UNKNOWN`; it does not intentionally forward them to the pane. Literal `11;rgb...` means the parser abandoned or lost the OSC prefix before completion, most plausibly at its partial-key timeout or because delivery began after tmux stopped expecting/recognizing that shape.
- Windows Terminal Core's `Terminal::ReturnResponse()` forwards each complete generated response in one callback call (`_pfnWriteInput(response)`). This establishes source-level message completeness but does not yet prove one atomic OS pipe write or ordering relative to separately generated keyboard/focus input.
- The 3.5a→3.6b parser changes around color replies mainly add theme-change notification and palette-query support; no obvious fix for OSC 10/11 BEL/ST recognition appeared in the narrowed diff.
- tmux 3.5a applies the ordinary `escape-time` to partial OSC 10/11 replies. Its default was reduced to 10 ms in the 3.5 generation, and an explicit `escape-time 0` becomes a 1 ms timer. tmux 3.6b commit `817b621d...` instead raises the deadline to at least 500 ms while a terminal query is outstanding. This explains why a byte-perfect response can leak only on older tmux or low-timeout configurations.
- Windows Terminal's current response delivery is already serialized at the terminal/pipe boundary: `ControlCore` appends all responses generated while parsing one output fragment into `_pendingResponses`, flushes that string once, and `ConptyConnection::WriteInput()` converts the complete UTF-16 string to UTF-8 under a FIFO ticket lock before issuing one overlapped `WriteFile`.
- The pseudo-terminal remains a byte stream, not a message transport. A single terminal `WriteFile` cannot guarantee one application `read()`, one SSH packet, or arrival before an application-selected deadline. Microsoft Terminal maintainers documented this exact boundary in issue #19282 and confirmed the response is already accumulated and written atomically.
- The exact tmux symptom is tracked in Microsoft Terminal #18004 and PowerShell/Win32-OpenSSH #2275. The affected path is Win32-OpenSSH, not response generation in Windows Terminal:
  - PowerShell/openssh-portable #771 replaced the 16-character console-input loop with a 1024-record bulk read, greatly reducing escape-sequence fragmentation.
  - PowerShell/openssh-portable #806 fixed `SIGWINCH` setting `EINTR` during a pending write, which caused a successfully written partial buffer to be retried/duplicated. This was the final fix cited when Terminal #18004 was closed.
- The current Terminal source already contains the major ConPTY stdin waiter-race fix from Microsoft Terminal #18816 (`299242176` in this history) as well as the response batching and raw pass-through fixes. Reapplying those fixes would be a no-op.
- The prior BEL workaround shortens OSC replies by one byte but cannot change PTY read boundaries, SSH packetization, application deadlines, or any CSI/DCS reply. It should not be represented as a root-cause fix.
- Codex #31420 is explicitly Linux over SSH and has a deterministic terminal-independent PTY reproducer. Even after fixing the Win32-OpenSSH transport defects, arbitrary network delay can cross Codex's 100 ms stdin-owner handoff. A general Codex fix requires one incremental input demultiplexer (or tracked outstanding replies) rather than any response suppression in Windows Terminal.
- A universal terminal-only guarantee is impossible under PTY semantics: replies and keys intentionally share the same byte stream, reads may split at every byte, and the terminal cannot observe when an application abandons a query. Suppressing, shortening, delaying, or rewriting replies would either remain timing-dependent or regress standards-compliant functionality.
- The ConPTY input parser had one avoidable split of its own: `StateMachine::FlushToTerminal()` passed `_cachedSequence` and `_CurrentRun()` to `ActionPassThroughString()` separately when an otherwise complete sequence spanned input reads. `InputStateMachineEngine` maps each callback to `InputBuffer::WriteString()`, and each call can wake an awaiting client. Thus ConPTY could manufacture two client-visible batches after correctly reassembling a response.
- The focused fix moves the cached prefix into a local string, appends the completing run, clears the cache, and invokes `ActionPassThroughString()` once. It changes callback granularity only; the concatenated UTF-16 byte sequence and order are identical to the prior two callbacks.
- Regression coverage now iterates every possible split boundary of the exact OSC 11 and Windows Terminal primary-DA replies, requiring zero pass-through calls before completion and exactly one afterward. A second test uses the actual `InputStateMachineEngine` and requires exactly one downstream input batch.
- The earlier OSC BEL change has been reversed. OSC replies again use the pre-existing ST terminator in 7-bit mode and C1 ST in S8C1T mode, so no response family is suppressed, shortened, or rewritten by the new fix.
- OpenAI Codex issue #31420 remains open on 2026-07-24. The official Codex manual does not document a user-facing fix for this internal startup-probe race, so the installer must not claim that a Terminal change can override Codex's own stdin deadline.
- The Win32-OpenSSH fixes relevant to this symptom are upstream PR #771 (larger console-input reads) and #806 (correct partial-write handling across `SIGWINCH`). Replacing or globally shadowing the user's SSH client would be a separate, potentially compatibility-affecting installation decision and is not silently included.

## Technical Decisions
| Decision | Rationale |
|----------|-----------|
| Instrument complete query/reply streams before editing | Visible tails omit control bytes, so guessing from display text is unsafe. |
| Separate the Codex parser race from any Windows Terminal transport defect | Issue #31420 proves a client-side failure with a synthetic terminal, but the user's repeatable Windows Terminal-vs-other-terminal tmux difference may still reveal a timing/fragmentation defect worth fixing at the transport layer. |
| Do not revert BEL solely on tmux-version speculation | Source inspection shows tmux 3.5a already accepts BEL for OSC color replies; timing/timeout behavior still needs direct reproduction. |
| Treat the user's SSH transport and the Codex stdin handoff as separate defects | Win32-OpenSSH has concrete fixed bugs that explain the repeatable tmux case; Codex's 100 ms reader handoff fails under a synthetic standards-compliant PTY even without Windows Terminal. |
| Do not claim a Terminal-only universal fix | PTYs do not preserve write boundaries, and Windows Terminal already performs one serialized write. Any terminal-side suppression would violate the no-functional-degradation requirement. |
| Remove ConPTY's avoidable parser boundary without claiming network atomicity | One pass-through callback is a real, compatibility-preserving improvement at the layer this fork controls; it cannot override an application's timeout after arbitrary SSH/network delay. |
